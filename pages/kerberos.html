Kerberos Deep Dive

Kerberos trades "prove your password every time" for "prove it once, then present time-limited tickets." That single design choice is why almost every high-impact AD attack technique revolves around stealing or forging tickets instead of cracking passwords.

AS Exchange → TGS Exchange → Service Access

sequenceDiagram participant C as Client participant KDC as KDC (Domain Controller) participant APP as Application Server C->>KDC: AS-REQ (username, timestamp encrypted with NT hash) KDC-->>C: AS-REP → TGT + Session Key
(TGT encrypted with krbtgt hash) Note over C: TGT cached, valid ~10 hours C->>KDC: TGS-REQ (TGT + SPN of target service) KDC-->>C: TGS-REP → Service Ticket
(encrypted with service account hash, contains PAC) C->>APP: AP-REQ (Service Ticket) APP->>APP: Decrypts ticket with its own hash, validates PAC APP-->>C: AP-REP → access granted

Step 1 — AS Request

The client proves knowledge of its password by encrypting a timestamp with its NT hash. If the KDC can decrypt it, it issues a TGT encrypted with the domain's krbtgt account hash — a secret only the KDC knows.

Step 2 — TGS Request

The client presents the TGT plus a target SPN. The KDC decrypts the TGT (proving it's genuine), builds a Service Ticket encrypted with that service account's hash, and embeds the client's PAC inside it.

PAC & SPN

Privilege Attribute Certificate (PAC)

A Microsoft extension to Kerberos embedded in the service ticket, carrying the user's SID, all group SIDs, and privileges — this is what lets the target server authorize the user without querying AD itself. It's signed by both the KDC and the target service key so tampering is detectable.

Service Principal Name (SPN)

A unique string like MSSQLSvc/db01.corp.local:1433 mapping a network service instance to the account that runs it. Kerberos can only issue a ticket for a service if its SPN is registered — no SPN means no Kerberos, forcing a fallback to NTLM (or failure).

Kerberos & NTLM Attack Techniques

These are the techniques every credential-theft discussion eventually lands on — understand the mechanism, not just the tool name.

CRITICAL

Golden Ticket

Forge a TGT from scratch using the stolen krbtgt account hash. Since the KDC trusts anything encrypted with that hash, the attacker can mint a TGT for any user (including ones that don't exist), with any group memberships, valid for up to 10 years by default. This bypasses AD entirely — it doesn't even need a real account.

MITIGATION
Rotate the krbtgt password twice (its history matters) after any suspected DC compromise; monitor Event ID 4768 for anomalous TGT requests and abnormal ticket lifetimes.
HIGH

Silver Ticket

Forge a Service Ticket using a stolen service account (or computer account) hash — no KDC contact required at all, since the target server validates the ticket itself. Scope is limited to that one service, but it's also far quieter (no Event ID 4769 at the DC).

MITIGATION
Enforce PAC validation on the target server; rotate service account passwords regularly; use group Managed Service Accounts (gMSA) with automatic rotation.
MEDIUM-HIGH

Kerberoasting

Any authenticated user can request a Service Ticket for any SPN. If that SPN belongs to a user account (not a computer account) with a weak password, the ticket — encrypted with that account's derived key — can be cracked offline at leisure.

MITIGATION
Use gMSAs (25+ character random passwords, auto-rotated) for service accounts; monitor Event ID 4769 for a burst of ticket requests with RC4 encryption (0x17) from one account.
MEDIUM

Pass the Ticket

Export a legitimately-issued TGT or service ticket from one session's memory and inject it into another session/machine, impersonating the ticket's owner without needing any password or hash.

MEDIUM

Pass the Hash

NTLM authentication only ever needs the NT hash, not the plaintext password. An attacker who dumps a hash from LSASS or the SAM can authenticate as that user anywhere NTLM is accepted, forever, until the password changes.

MEDIUM

NTLM Relay

Instead of cracking or reusing a hash, the attacker sits in the middle and relays a live NTLM handshake to a different server in real time — authenticating as the victim on a target they never intended to connect to.

MITIGATION
Enable SMB signing and Extended Protection for Authentication (EPA); disable NTLM where feasible; enforce LDAP/LDAPS signing and channel binding.

Modern Defenses

Credential Guard

Uses Virtualization-Based Security (a hypervisor-isolated VTL1 enclave) to run LsaIso.exe, holding NTLM hashes and Kerberos TGT keys where not even a kernel-mode exploit in the normal OS can reach them. LSASS in the normal OS only holds derived, single-use material.

LSA Protection (RunAsPPL)

Marks lsass.exe as a Protected Process (Light) at the ELAM/signing level, so only other signed, protected processes can open handles to it — blocking the classic OpenProcess + dump approach used by tools like Mimikatz (though kernel-level attacks and driver abuse can still bypass it).

Cached Credentials & Offline Login

Laptops need to log in without a network path to a Domain Controller. Windows solves this with cached domain credential verifiers — not the password, not even the NT hash, but a salted, iterated hash of the last successful domain logon (MSCacheV2), stored per user.

Registry LocationPurpose
HKLM\SECURITY\CacheStores the cached domain verifiers (NL$1…NL$10 by default).
HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon!CachedLogonsCountHow many prior domain logons are cached (0 disables offline logon entirely).
SECURITY NOTE
Cached verifiers are intentionally not directly usable for Pass-the-Hash or network authentication — they can only be brute-forced offline, which is why they're a lower-value (but not zero-value) target than a live NT hash.
DID YOU KNOW?
A default-configuration TGT is valid for 10 hours and renewable for 7 days — meaning a stolen ticket doesn't even need to be used immediately to still be dangerous a week later.
