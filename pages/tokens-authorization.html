Access Tokens & Authorization

Authentication answers "who are you?" exactly once, at logon. Everything after that — every file open, every registry write, every process launch — is answered by the Access Token LSASS built at that moment, checked by the Security Reference Monitor every single time.

Anatomy of an Access Token

User SID

A unique, never-reused identifier for the account (e.g. S-1-5-21-...-1001). The final component is the RID — 500 is always the built-in Administrator, 501 Guest.

Group SIDs

Every group the user belongs to, direct and nested — this list is what most DACL checks actually match against.

Privileges

Named rights like SeDebugPrivilege or SeImpersonatePrivilege that bypass normal object-level checks entirely — these are frequently the real privilege-escalation lever, not the SID list.

Integrity Level

Low / Medium / High / System, enforced by Mandatory Integrity Control — independent of and stricter than the DACL: a lower-integrity process cannot write to a higher-integrity object no matter what the DACL says.

Primary vs Impersonation Tokens
A primary token is attached to a process at creation and defines its default security context. An impersonation token is adopted temporarily by a single thread — e.g. a file server thread "becomes" the connecting client just long enough to check that client's file permissions, then reverts.

Object Manager

The Executive component managing the entire kernel object namespace — files, processes, sections, mutexes — as a unified tree, so every object type gets security enforcement for free.

Security Reference Monitor

The kernel-mode gatekeeper, inside ntoskrnl.exe, that performs the actual access check comparing a token to a Security Descriptor — nothing in user mode can bypass it.

Security Descriptor

The structure attached to every securable object: owner SID, group SID, a DACL, and a SACL.

UAC

When an administrator logs on, LSA actually builds two tokens — a filtered standard-user token used by default, and a full admin token used only after an explicit elevation prompt. This is why "Run as Administrator" exists as a distinct action.

DACL, SACL & NTFS Permissions

ConceptWhat it controls
DACLWhich SIDs are allowed/denied which access rights — the "permissions" users normally see and edit.
SACLWhich operations get written to the Security event log — auditing, not access control.
NTFS PermissionsDACLs applied specifically to files/folders (Full Control, Modify, Read & Execute, Write) — combine with share permissions, most restrictive wins.
InheritanceChild objects inherit ACEs from their parent container unless explicitly blocked — the majority of real-world permission misconfigurations come from broken inheritance assumptions.
DID YOU KNOW?
Mandatory Integrity Control was added specifically to stop admin-level malware from silently tampering with browser processes — it's why a "Low" integrity sandboxed browser process can't write to your Documents folder even if the DACL would technically allow it.
