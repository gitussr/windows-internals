Windows Attack Techniques

Every technique here is a documented, publicly-known abuse of a legitimate Windows mechanism you've already read about. Understanding the mechanism is what lets a defender recognize it — the "how" always comes with a link back to the internals that make it possible.

CREDENTIAL ACCESS

LSASS Memory Dumping

Open a handle to lsass.exe with PROCESS_VM_READ, then call MiniDumpWriteDump (directly, or via the comsvcs.dll MiniDump export as a living-off-the-land trick) to write LSASS's memory to disk for offline parsing of credential material. See lsass.exe internals.

RED TEAM NOTE
RunAsPPL and Credential Guard both raise the bar significantly — a straight OpenProcess handle grab fails against a protected LSASS, forcing attackers toward kernel-level tricks or targeting endpoints where those protections aren't enabled.
CREDENTIAL ACCESS

Kerberos Abuse

Kerberoasting, Golden/Silver Tickets, and Pass the Ticket — covered in full in the Kerberos Deep Dive. The common thread: Kerberos trusts anything encrypted with the right key, so stealing or cracking the right key (service account password, or the krbtgt hash) is as good as authenticating normally.

CREDENTIAL ACCESS / LATERAL MOVEMENT

NTLM Abuse

Pass the Hash and NTLM Relay — see Kerberos Deep Dive. NTLM's stateless challenge-response design means the hash alone is a complete credential; a coercion technique (e.g. forcing a server to authenticate to an attacker-controlled listener) can trigger a relay without any user interaction at all.

PERSISTENCE / PRIV ESC

Service Abuse

Create a new service (sc.exe create) or hijack an existing one's ImagePath/binPath to run arbitrary code as SYSTEM at boot. Weak service permissions (a writable binary path, or a modifiable service config) let a low-privilege user escalate by pointing an existing SYSTEM-run service at their own binary.

PERSISTENCE

Registry Persistence

Run/RunOnce keys, Winlogon Shell/Userinit hijack, and IFEO Debugger redirection — see the full autostart locations table. All of these are legitimate OS features; the abuse is purely in what gets pointed at them.

PERSISTENCE

Scheduled Task Abuse

Register a task (schtasks.exe /create) that runs at logon, on a schedule, or on a specific event trigger — commonly hosted via taskhostw.exe, and often configured to run as SYSTEM with "Run whether user is logged on or not."

EXECUTION / PERSISTENCE / LATERAL MOVEMENT

WMI Abuse

WMI provides both remote execution (wmic process call create — no new listening port, rides over existing RPC/DCOM) and persistence via WMI Event Subscriptions (a permanent event filter + consumer pair that fires a payload on a system event, entirely invisible to the Run-keys/Services/Scheduled-Tasks checklist most responders reach for first).

EXECUTION / DEFENSE EVASION

PowerShell Abuse

Fileless execution directly in memory (IEX (New-Object Net.WebClient).DownloadString(...) patterns), AMSI bypass attempts, and heavy obfuscation (Base64 + gzip, string concatenation) to slip past signature-based detection — countered primarily by Script Block Logging capturing the de-obfuscated content regardless of how it was written on the wire.

DEFENSE EVASION / PRIV ESC

DLL Search Order Hijacking

Windows searches for a DLL in a defined order (the application's own directory first, then system directories, then PATH). Dropping a malicious DLL with the exact name of a legitimate one somewhere earlier in that search order gets it loaded by a legitimate, often signed, host process — useful for both persistence and evading allow-listing that only checks the parent EXE.

PERSISTENCE / DEFENSE EVASION

COM Hijacking

Overwrite a COM class's InprocServer32 registration — often in the per-user, no-admin-required HKCU\Software\Classes\CLSID\{GUID} path (backed by UsrClass.dat) — so that any legitimate application instantiating that CLSID unknowingly loads the attacker's DLL instead.

DID YOU KNOW?
WMI Event Subscriptions are one of the oldest persistence tricks still in wide use precisely because they leave no file on disk and no entry in Run keys, Services, or Scheduled Tasks — they live entirely inside the WMI repository (OBJECTS.DATA).
