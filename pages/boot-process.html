Part 1 · Boot & Process Architecture

Windows Boot Process

From the moment power hits the board to the moment explorer.exe paints the desktop, Windows runs a strict, layered chain of trust. Every stage exists to hand off to the next one only after verifying it's allowed to.

Evolution of the Logon Architecture

WINDOWS NT 3.1 – 4.0
GINA-based logon

Winlogon delegates all UI and credential collection to a single, replaceable Graphical Identification and Authentication DLL (msgina.dll). Simple, but any third party GINA replacement fully owns the logon experience — a huge trust surface.

WINDOWS XP / 2003
GINA matures, fast user switching arrives

Same GINA model, now with the Welcome Screen, fast user switching (via Terminal Services sessions), and wider LSA authentication package support.

WINDOWS VISTA
GINA is dead. Credential Providers arrive.

GINA is replaced entirely by logonui.exe hosting pluggable, COM-based Credential Providers. Session 0 isolation separates services from interactive user sessions. UAC and Mandatory Integrity Control ship for the first time.

WINDOWS 10
Windows Hello, Credential Guard, VBS

Biometric and PIN-based Credential Providers backed by TPM-protected keys (Windows Hello for Business). Credential Guard uses Virtualization-Based Security to move NTLM hashes and Kerberos keys out of reach of the normal kernel.

WINDOWS 11
TPM 2.0 mandatory, LSA protection by default

TPM 2.0 and Secure Boot become hard installation requirements. LSA Protection (RunAsPPL) and Credential Guard are enabled by default on new hardware; passkeys extend Hello beyond the local device.

The Firmware Trust Chain

BIOS (Legacy)

16-bit real-mode firmware, MBR partitioning, no built-in signature checking. It hands off blindly to whatever code sits in the boot sector — the reason bootkits thrived for a decade.

UEFI

Unified Extensible Firmware Interface — a full pre-OS execution environment with GPT partitioning, network stack, and a driver model. It is what makes Secure Boot possible.

Secure Boot

UEFI verifies the digital signature of bootmgfw.efi (Windows Boot Manager) against keys in firmware (PK/KEK/db/dbx) before executing it. An unsigned or tampered loader is refused outright.

TPM & BitLocker

The TPM measures each boot stage into PCRs (Platform Configuration Registers). BitLocker seals the volume master key to those PCR values, so the drive only auto-unlocks if the measured boot chain matches — change anything upstream and it demands the recovery key.

HOW MEASURED BOOT WORKS
Each stage hashes the next stage's code before handing off control, and extends that hash into a TPM PCR. Secure Boot answers "is this signed by someone I trust?"; measured boot answers "exactly what ran, byte for byte?" — BitLocker keys off the second answer.

Windows Boot Manager → Kernel

bootmgfw.efi / bootmgr

Loaded by UEFI firmware (or the MBR/VBR chain on legacy BIOS as bootmgr). Its only job: read the Boot Configuration Data store and present/select the OS entry, then launch the matching OS loader.

BCD — Boot Configuration Data

A registry-format hive (\EFI\Microsoft\Boot\BCD) replacing the old boot.ini. Managed with bcdedit.exe; stores boot entries, timeout, the default OS, and Advanced Boot options (Safe Mode, debug, test-signing).

winload.efi

The OS loader. Validates its own signature, loads ntoskrnl.exe, hal.dll, the boot-start drivers listed in the registry (Start=0), and the SYSTEM registry hive itself — then transfers CPU control to the kernel entry point.

ntoskrnl.exe + HAL

The kernel initializes the Executive subsystems (Object Manager, Memory Manager, Security Reference Monitor, I/O Manager, Process Manager), using hal.dll to talk to hardware without knowing chipset specifics. It builds the first process (System, PID 4) and its first thread creates smss.exe.

Boot order at a glance

  1. UEFI firmware → Secure Boot signature check
  2. bootmgfw.efi reads BCD
  3. winload.efi loads kernel, HAL, boot drivers, SYSTEM hive
  4. ntoskrnl.exe initializes Executive, starts smss.exe
  5. smss.exe → csrss.exe + wininit.exe (session 0)
  6. wininit.exe → services.exe (SCM) + lsass.exe
  7. smss.exe → csrss.exe + winlogon.exe (session 1)
  8. winlogon.exe → logonui.exe → credential providers

smss.exe — Session Manager Subsystem

The very first user-mode process. There is no parent process shown for it in Task Manager because it's created directly by a kernel-mode system thread, not by another user-mode process.

RESPONSIBILITIES

Creates environment variables, opens paging files, creates the initial three sessions, runs BootExecute native applications (e.g. autochk), processes pending file rename/delete operations, then spawns csrss.exe + wininit.exe/winlogon.exe per session and exits its per-session copy (the master instance keeps running to service new session requests).

REGISTRY INTERACTION

HKLM\SYSTEM\CurrentControlSet\Control\Session Manager — BootExecute, PendingFileRenameOperations, SubSystems\Windows, Memory Management\*, Environment.

DLL DEPENDENCIES

Deliberately minimal — mostly ntdll.dll only (native API, no Win32 subsystem yet exists when it starts).

MEMORY / KERNEL INIT

Runs before any Win32 subsystem exists, so it can only call the Native API (Nt*/Zw* functions) directly — no kernel32.dll. It creates the paging file(s) sized per Memory Management registry values.

RED TEAM NOTE
A malicious BootExecute entry runs before Defender's real-time protection is fully online — a rare pre-AV persistence window. Extremely high-value, extremely rare in practice because it requires SYSTEM + a reboot.

The Logon Process Cast

Eleven processes, one job each. For every one: purpose, launcher, DLLs, registry, privileges, and how it gets abused.

SYSTEM

winlogon.exe

Purpose: Owns the secure desktop, listens for the Secure Attention Sequence (Ctrl+Alt+Del), drives the logon/lock/unlock state machine, launches the shell via userinit.exe.

Launched by: smss.exe, one instance per interactive session.

DLLs loaded: winsta.dll, sas.dll, wlnotify.dll (legacy notify packages), userenv.dll.

Registry: HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon — Shell, Userinit, GinaDLL (legacy), AutoAdminLogon.

Privileges: SYSTEM, exclusive access to the Winlogon secure desktop.

Abuse: Append a second binary to Shell or Userinit for boot persistence; register a rogue Credential Provider CLSID.

DETECTION
Baseline Shell=explorer.exe and Userinit=C:\Windows\system32\userinit.exe, exactly; alert on any extra comma-separated value or path outside System32.
SYSTEM

logonui.exe

Purpose: Renders the actual logon screen and hosts Credential Provider tiles on the secure desktop.

Launched by: winlogon.exe, fresh process every time the SAS fires.

DLLs loaded: authui.dll, credui.dll, plus every registered Credential Provider COM DLL (e.g. cryptngc.dll for Hello).

Registry: HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Authentication\Credential Providers\{GUID}.

Privileges: SYSTEM, isolated on the secure desktop — no other desktop's windows can draw over it.

Abuse: Not logonui.exe itself, but adjacent accessibility-tool hijacks — replacing sethc.exe/utilman.exe or setting an IFEO Debugger on them to spawn cmd.exe as SYSTEM before any credentials are entered.

RED TEAM NOTE
"Sticky Keys" backdoor: replace C:\Windows\System32\sethc.exe with cmd.exe (needs offline/admin access), then pressing Shift 5x at the lock screen pops a SYSTEM shell.
SYSTEM · PPL

lsass.exe

Purpose: Enforces the local security policy — authentication, token creation, holds credential secrets in memory. See Part 2 for the full authentication engine.

Launched by: wininit.exe, in Session 0.

DLLs loaded: lsasrv.dll, msv1_0.dll, kerberos.dll, negotiate.dll, schannel.dll, samsrv.dll.

Registry: HKLM\SYSTEM\CurrentControlSet\Control\Lsa — Authentication Packages, Security Packages, RunAsPPL.

Privileges: SYSTEM; can run as a Protected Process Light (PPL) since RunAsPPL=1, or isolated entirely via Credential Guard.

Abuse: The single most targeted process on Windows for credential dumping (Mimikatz sekurlsa::logonpasswords).

DETECTION
Sysmon Event ID 10 (ProcessAccess) with TargetImage=lsass.exe and GrantedAccess of 0x1010/0x1410/0x1fffff from a non-allow-listed source process; Defender ASR rule "Block credential stealing from the Windows local security authority subsystem".
SYSTEM

services.exe

Purpose: Service Control Manager (SCM) — starts, stops, and supervises every Windows service per its configured start type.

Launched by: wininit.exe, Session 0.

DLLs loaded: sechost.dll, advapi32.dll, rpcrt4.dll.

Registry: HKLM\SYSTEM\CurrentControlSet\Services\* — ImagePath, Start, Type, ObjectName.

Privileges: SYSTEM.

Abuse: Create a new service (or overwrite ImagePath on an existing one) pointing to a malicious binary for persistence and lateral movement (PsExec-style).

DETECTION
Event ID 7045 (new service installed) and 4697 (service installed, Security log); alert on services.exe spawning cmd.exe/powershell.exe directly.
SYSTEM

smss.exe

Covered in full above — see Session Manager Subsystem.

SYSTEM · PROTECTED

csrss.exe

Purpose: User-mode half of the Win32 subsystem — console window hosting, process/thread creation & termination notifications, shutdown coordination.

Launched by: smss.exe, one per session.

DLLs loaded: csrsrv.dll, basesrv.dll, winsrv.dll.

Registry: HKLM\SYSTEM\CurrentControlSet\Control\Session Manager\SubSystems!Windows.

Privileges: SYSTEM, marked a critical process — the kernel bugchecks the machine if it's killed.

Abuse: Rarely a direct target today; an extra csrss.exe not spawned by smss.exe is a strong process-masquerading indicator.

USER

explorer.exe

Purpose: The Windows shell itself — desktop, taskbar, Start menu, File Explorer windows.

Launched by: userinit.exe, per the Shell value; userinit then exits.

DLLs loaded: shell32.dll, shcore.dll, explorerframe.dll, windows.storage.dll.

Registry: HKCU\...\Explorer shell folders and CLSID extension points; Winlogon!Shell.

Privileges: The logged-on user's token (Medium integrity, or a filtered admin token under UAC).

Abuse: Malicious shell extensions / context-menu handlers; classic process-name masquerading (fake explorer.exe launched from a temp folder).

DETECTION
Verify image path is exactly C:\Windows\explorer.exe and parent process is userinit.exe; anything else is suspicious.
USER

userinit.exe

Purpose: Applies profile/logon-script environment setup, then launches the Shell and terminates.

Launched by: winlogon.exe, per the Userinit value, after a successful logon.

DLLs loaded: userenv.dll.

Registry: HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Winlogon!Userinit.

Privileges: The freshly created user token; short-lived.

Abuse: Append ,C:\malware.exe to the Userinit value — runs at every single logon, before the shell even appears.

USER

dwm.exe

Purpose: Desktop Window Manager — GPU-accelerated window composition, transparency, and visual effects, one instance per session.

Launched by: Session infrastructure at session creation (via winlogon/session manager).

DLLs loaded: dwmcore.dll, uDWM.dll, d3d11.dll.

Registry: HKCU\Software\Microsoft\Windows\DWM.

Privileges: Runs as the logged-on user since Windows 8 (previously a dedicated service account).

Abuse: Rarely targeted directly; occasionally seen as a masquerading process name.

VARIES

taskhostw.exe

Purpose: Generic host for DLL/COM-based Scheduled Tasks that don't warrant their own executable.

Launched by: Task Scheduler service, at logon or on a task trigger.

DLLs loaded: Whatever the hosted task specifies, plus taskschd.dll.

Registry: HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Schedule\TaskCache; task XML in C:\Windows\System32\Tasks.

Privileges: Whatever the task's configured principal is — often SYSTEM.

Abuse: A very common persistence host — register a task whose action loads an attacker DLL/COM handler.

DETECTION
Event ID 4698 (scheduled task created); review Task Cache registry and Tasks folder XML for unfamiliar actions.
VARIES

svchost.exe

Purpose: Generic host process for services implemented as DLLs, grouped by the -k switch to share or isolate processes.

Launched by: services.exe (SCM).

DLLs loaded: Each service's ServiceDll value.

Registry: HKLM\SYSTEM\CurrentControlSet\Services\<svc>\Parameters!ServiceDll; HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\Svchost (group definitions).

Privileges: LocalSystem, LocalService, or NetworkService depending on the service.

Abuse: The most typo-squatted / masqueraded process name in the wild; also abused by registering a malicious ServiceDll under a legitimate-sounding service.

DETECTION
Validate path is exactly C:\Windows\System32\svchost.exe, parent is services.exe, and the -k group argument matches a known-good group; flag any svchost.exe with no -k argument.
DID YOU KNOW?
Session 0 stopped hosting interactive user desktops starting with Vista specifically to prevent "shatter attacks," where a low-privilege process sends window messages to a higher-privilege one sharing the same desktop.
