Part 2 · The Authentication Engine

Windows Authentication

Every logon — console, RDP, or network — funnels through the same engine: a Credential Provider collects material, Winlogon hands it to LSASS, and an Authentication Package validates it against the SAM or Active Directory before a token is minted.

The Full Authentication Sequence

Credential Providers

A Credential Provider is a COM object implementing ICredentialProvider, registered under HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Authentication\Credential Providers. logonui.exe enumerates every registered provider and renders one tile per provider, per available factor.

Password Provider

The default tile. Serializes the password into a KERB_INTERACTIVE_LOGON structure and hands it to Winlogon — the password never touches disk, only process memory in transit to LSASS.

Windows Hello (Biometric / PIN)

The PIN or biometric never leaves the device and never authenticates to AD directly — it unlocks a TPM-protected asymmetric key pair (or on-device secure enclave), and that key signs the actual authentication request. A stolen PIN is useless on another machine.

Smart Card

Uses the certificate on the card plus a PIN to unlock the card's private key, performing certificate-based Kerberos pre-authentication (PKINIT) directly against the KDC.

Biometric (Fingerprint / Face)

Captured and matched locally by the Windows Biometric Framework; on a match it releases the Hello key exactly like the PIN flow above — biometric data itself is never sent anywhere.

CREDPROV.DLL
There's no single literal credprov.dll shipped by Microsoft for every provider — it's a generic name for the pattern: each provider (password, Hello, smart card) is its own signed COM DLL implementing the same ICredentialProvider/ICredentialProviderCredential interfaces that logonui.exe calls into.

Authentication Packages & Security DLLs

These DLLs load inside lsass.exe (or are called by every process via secur32.dll) and together implement every credential validation path Windows supports.

msv1_0.dll NTLM Authentication Package

Purpose: Implements NTLM challenge-response and validates local logons against the SAM.

Functions: LsaApLogonUser, NTLM challenge/response computation.

Loaded by: lsasrv.dll inside lsass.exe, via the Authentication Packages list.

Dependencies: samsrv.dll/samlib.dll for local SAM lookups, netlogon.dll for domain pass-through.

Registry: HKLM\SYSTEM\CurrentControlSet\Control\Lsa!Authentication Packages.

Security implications: Computes and briefly holds NTLM hashes in LSASS memory — the core of Pass-the-Hash.

kerberos.dll Kerberos SSP/AP

Purpose: Implements Kerberos v5 (RFC 4120) — AS-REQ/REP, TGS-REQ/REP, and ticket caching.

Functions: KerbLogonUser, ticket cache management (visible via klist).

Loaded by: lsasrv.dll, via the Security Packages list.

Dependencies: cryptdll.dll for crypto primitives, DNS for KDC discovery.

Registry: HKLM\SYSTEM\CurrentControlSet\Control\Lsa\Kerberos\Parameters.

Security implications: The in-memory ticket cache is the target for Pass-the-Ticket, Golden/Silver Ticket use.

wdigest.dll Digest Auth

Purpose: Implements HTTP/SASL Digest authentication (RFC 2617).

Functions: DigestLogonUser.

Loaded by: lsasrv.dll.

Dependencies: None significant.

Registry: HKLM\SYSTEM\CurrentControlSet\Control\SecurityProviders\WDigest!UseLogonCredential.

Security implications: Historically cached a reversibly-encrypted, effectively-plaintext password in LSASS. Disabled by default since KB2871997 (UseLogonCredential=0) — but re-enabling it is a common attacker move post-compromise.

tspkg.dll Terminal Services Package

Purpose: Supports credential caching for Terminal Services / RDP "save my credentials" and CredSSP-based flows.

Functions: Credential storage/retrieval helpers for RDP sessions.

Loaded by: lsasrv.dll.

Dependencies: credssp.dll.

Registry: Security Packages list.

Security implications: Like WDigest, historically a Mimikatz target for recovering stored RDP credentials.

pku2u.dll Peer-to-Peer Auth

Purpose: PKU2U — certificate-based peer-to-peer authentication without a domain or KDC (e.g. device-to-device sharing).

Functions: Local CA-signed cert exchange and mutual authentication.

Loaded by: lsasrv.dll.

Dependencies: cryptdll.dll, certificate store APIs.

Registry: HKLM\SYSTEM\CurrentControlSet\Control\Lsa\pku2u!AllowOnlineID.

Security implications: Rarely used in managed enterprises; commonly disabled via policy to shrink the authentication attack surface.

Negotiate.dll SPNEGO

Purpose: Meta-package that picks Kerberos when possible, falling back to NTLM automatically.

Functions: Package negotiation / selection logic.

Loaded by: lsasrv.dll.

Dependencies: kerberos.dll, msv1_0.dll.

Registry: Security Packages list ("Negotiate").

Security implications: The silent Kerberos→NTLM downgrade path — attackers can force SPN resolution to fail so a client falls back to weaker NTLM, enabling relay attacks.

schannel.dll TLS/SSL SSP

Purpose: Implements TLS/SSL/DTLS for RPC, LDAPS, and HTTPS-based Windows components.

Functions: Certificate-based mutual auth, session key negotiation.

Loaded by: lsasrv.dll and directly by network services (IIS, RDP/CredSSP).

Dependencies: bcrypt.dll/ncrypt.dll, the certificate store.

Registry: HKLM\SYSTEM\CurrentControlSet\Control\SecurityProviders\SCHANNEL (protocol/cipher policy).

Security implications: Misconfigured protocol/cipher registry values enable downgrade attacks; certificate validation flaws here are critical severity.

lsasrv.dll LSA Server Core

Purpose: The core LSA server logic — orchestrates every authentication/security package, the policy database, and token creation.

Functions: LsaLogonUser dispatch, LsaAddAccountRights, policy object management.

Loaded by: lsass.exe directly at process start.

Dependencies: Every authentication package DLL on this page.

Registry: The entire HKLM\SYSTEM\CurrentControlSet\Control\Lsa tree.

Security implications: This is the trust boundary — full compromise of this DLL's process means full compromise of the machine's credential material.

samlib.dll / samcli.dll SAM Client

Purpose: Client-side RPC access to the SAM database, local or remote.

Functions: SamConnect, SamOpenUser, group/user enumeration.

Loaded by: lsass.exe, admin snap-ins (Local Users & Groups), auditing tools.

Dependencies: rpcrt4.dll for RPC transport.

Registry: The HKLM\SAM hive itself — access-restricted even to local Administrators by default ACL.

Security implications: Target of local hash extraction via reg save HKLM\SAM + offline parsing.

cryptdll.dll Crypto Primitives

Purpose: Core cryptographic primitives for Kerberos/NTLM — DES/RC4/HMAC and NT-hash key derivation.

Functions: CDLocateCSystem, hash/HMAC helper routines.

Loaded by: kerberos.dll, msv1_0.dll.

Dependencies: bcrypt.dll (modern CNG backend).

Registry: FIPS algorithm policy keys can restrict which primitives are permitted.

Security implications: Implements NTOWFv1/v2 (NT hash derivation) — foundational to why Pass-the-Hash works at all.

advapi32.dll Base Security API

Purpose: Exposes registry, service control, event log, and security APIs to every user-mode process.

Functions: LogonUserW, OpenProcessToken, AccessCheck, RegOpenKeyEx.

Loaded by: Nearly every process on the system.

Dependencies: sechost.dll, rpcrt4.dll.

Registry: n/a — it's a general API surface, not a policy owner.

Security implications: The primary API surface attackers call for credential validation testing, token manipulation, and service creation.

secur32.dll SSPI Dispatcher

Purpose: Public SSPI surface — AcquireCredentialsHandle, InitializeSecurityContext, AcceptSecurityContext — routing to whichever package is selected.

Functions: SSPI dispatch to NTLM/Kerberos/Negotiate/Schannel backends.

Loaded by: Any process doing network auth — browsers, RDP clients, SQL clients.

Dependencies: RPCs into lsasrv.dll inside lsass.exe for the real logic.

Registry: HKLM\SYSTEM\CurrentControlSet\Control\SecurityProviders (package list).

Security implications: The client-facing seam where NTLM relay and protocol downgrade attacks are launched from.

netlogon.dll Netlogon / Zerologon Surface

Purpose: Implements the Netlogon secure channel between a member computer and a DC, NTLM pass-through, and DC discovery.

Functions: NetrServerReqChallenge, NetrServerAuthenticate.

Loaded by: Hosted inside lsass.exe as the Netlogon service, given its security sensitivity.

Dependencies: msv1_0.dll for pass-through NTLM, DNS client for DC lookup.

Registry: HKLM\SYSTEM\CurrentControlSet\Services\Netlogon\Parameters!FullSecureChannelProtection.

Security implications: CVE-2020-1472 "Zerologon" exploited a crypto flaw here to reset a DC's machine account password and seize domain admin.

userenv.dll User Environment

Purpose: Applies Group Policy and loads/unloads the user's registry profile (NTUSER.DAT).

Functions: LoadUserProfile, CreateEnvironmentBlock, ProcessGroupPolicy.

Loaded by: winlogon.exe/userinit.exe, and the Group Policy Client service.

Dependencies: profapi.dll.

Registry: Mounts HKCU; reads policy under Software\Policies.

Security implications: Group Policy tampering here is a domain-wide persistence and privilege-escalation vector.

profapi.dll Profile API

Purpose: Lower-level profile mount/unmount routines used by userenv.dll.

Functions: Underlying LoadUserProfileW/UnloadUserProfile implementations.

Loaded by: userenv.dll, winlogon.exe.

Dependencies: Native hive-loading calls in ntdll.dll.

Registry: HKLM\SOFTWARE\Microsoft\Windows NT\CurrentVersion\ProfileList (per-SID ProfileImagePath).

Security implications: ProfileList tampering can redirect a profile path or leave orphaned, readable hives behind.

profsvc User Profile Service

Purpose: Service-side coordination of profile load/unload lifecycle tied to logon/logoff events.

Functions: Signals userenv.dll/profapi.dll at the right lifecycle points.

Loaded by: services.exe starts it as an auto-start service, hosted in a shared svchost.exe.

Dependencies: profapi.dll, userenv.dll.

Registry: HKLM\SYSTEM\CurrentControlSet\Services\ProfSvc.

Security implications: Failures here cause temporary profile logons — a useful timing signal, not a common direct attack surface.

DID YOU KNOW?
Windows Hello's "PIN is more secure than a password" claim isn't about PIN complexity — a 4-digit PIN is trivially guessable. It's secure because it never leaves the device and is useless without the TPM-bound key it unlocks.
